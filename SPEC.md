# ATIP product + UI specification (canonical)

## Outcome and user journey
ATIP is a production-oriented, multi-tenant autonomous testing intelligence platform for developers and small teams. A user signs in, connects a GitHub App installation, selects a repository/branch/PR, mines commit history and dependencies, sees evidence-backed risk, reviews a suggested test plan, approves permitted actions, executes tests in a secure sandbox, investigates failures with AI, and publishes results as GitHub checks/reports. Everything is organization-scoped and auditable.

## Design: LOCKED
**No landing page in scope.** App UI is Claude-inspired but original: quiet, classy, monochrome, practical. Light default and dark optional. Typography `Figtree` for body/UI, `Source Serif 4` for rare editorial headings (fallback sans/serif); no imitation of proprietary branding. Palette light `#FAFAF8` canvas, `#FFFFFF` surfaces, `#171717` text, `#737373` secondary, `#E5E5E5` borders; dark `#101010`, `#181818`, `#F5F5F5`, `#A3A3A3`, `#333333`. State colors limited and accessible; monochrome icons/status text must still communicate meaning. Sidebar width ~240px, collapsible to icons; header ~64px; max content width ~1440px; radius 8–12px; 1px borders; restrained shadows; tables not cards for dense data; no glassmorphism, gradients, 3D, neon or perpetual animation. Prefer skeletons, empty states, keyboard focus, responsive drawers. **Use `design/ATIP_Six_Screens_Exact_Crops/ATIP_APPROVED_SIX_SCREEN_REFERENCE.png` and the six individual images in that folder as primary visual references; `design/ui-reference.html` is the secondary functional/interaction reference. Every route must support both themes; the reference images do not prescribe fixed per-page themes.** Implement equivalent production components in Next.js, do not ship HTML as the final app.

## Routes, interactions and content (implement UI in M0)
1. `/app` **Overview:** org/repo switcher; 4 stat summaries (repositories, analyses, high-risk findings, test pass rate); recent activity; active runs; primary `Connect repository` / `Analyze repository` CTA; real empty/loading/error states.
2. `/app/repositories` **Repositories:** search/filter/sort; GitHub connection status; repo table (name, branch, last sync, analysis, risk); connect/manage installation CTA; selection/navigation.
3. `/app/repositories/[id]` **Repository workspace:** header/branch selector; tabs Overview, Commits, Files, Dependencies, Coverage; analysis CTA; file drilldown, dependency explorer (React Flow with list fallback); source evidence and timestamps.
4. `/app/risk` **Risk intelligence:** repo/branch/PR filters; ranked risky files/modules, score (0–100), reasons and confidence; severity chips, sort/filter; detail drawer with commits/complexity/coverage evidence; distinguish missing data.
5. `/app/test-plans` **Test plans:** plans table, plan detail, selected tests, proposed generated tests, rationale and expected coverage; draft/review/approved/rejected status; approvals only with correct role and server policy.
6. `/app/runs` **Test runs:** queue/running/completed/failed/cancelled; repo, commit, duration, status; filtering and drilldown; start/cancel only if allowed.
7. `/app/runs/[id]` **Run details:** stepper, live event stream, stdout/stderr, individual tests, artifacts/coverage, retry/cancel controls, reason for sandbox failure, timestamps; do not imply unsafe execution is available.
8. `/app/analysis` **AI analysis:** Claude-like split-pane conversational investigation UI; selectable failed run; evidence citations, hypothesis vs confirmed facts, model/provider and cost, suggestions and approval gate for PR/patch.
9. `/app/reports` **Reports:** quality trends, risk over time, run summaries, filters/date range, CSV/JSON download and shareable organization-scoped links if authorized; charts with accessible table alternatives.
10. `/app/settings` **Settings:** Profile, Organization, Members/Roles, GitHub, AI Providers, Execution Policies, Notifications, Audit, Appearance; secrets masked, provider consent explicit.
11. `/sign-in` + auth callback/error views: OIDC sign-in, organization selection and session failure.

Navigation: sidebar Overview, Repositories, Risk Intelligence, Test Plans, Test Runs, AI Analysis, Reports; Settings pinned bottom. Top bar org switcher, repository context, search, theme and profile. Desktop and mobile both functional. Every route needs loading/empty/error/permission-denied states and sensible demo fixtures during M0, visually marked `Demo data` until real API is connected.

## Functional contract
- Auth: OIDC, secure session, org membership, roles Owner/Admin/Maintainer/Developer/Viewer, tenant-aware backend enforcement, org switch, invite/manage membership and audit.
- GitHub: installation flow, least-privilege scopes, repo discovery, sync and pagination, branch/PR selection, signed webhook verification, replay/dedup, GitHub checks and optional approved PR comments.
- Mining: immutable commit snapshots, commits/diffs, file changes, authorship, change frequency, defect-linked commits where evidence supports it, Python and JS/TS parsers, static complexity, import/dependency graph, test discovery, coverage import and provenance.
- Risk: versioned deterministic baseline score with documented feature weights, change impact, test gaps, explainable evidence links, confidence/missing-data signals, no fabricated predictive accuracy.
- Predictive ML: develop an optional independently evaluated supervised risk-prediction model (e.g. LightGBM/XGBoost) only when sufficient permissioned, reliably labeled history exists. Specify prediction target (e.g. future defect-linked change), observation window, label provenance, missing/uncertain labels, class imbalance, and feature availability at prediction time. Compare against deterministic baseline; do not call heuristic scores ground truth. Train with temporal and repository-held-out splits, avoid leakage from future commits/test results, evaluate calibration and precision/recall/PR-AUC and operational usefulness, and publish model/data version and limitations. If dataset is inadequate, keep baseline active and report training as blocked/unvalidated, not completed.
- ML operations: reproducible dataset construction and feature pipelines, training/evaluation commands, artifact registry or versioned storage, approved promotion, inference adapter, rollback, drift/quality monitoring, privacy/retention controls, and controlled retraining. Do not train foundation LLMs as a prerequisite; use pretrained LLM providers for test generation and investigation.
- Test intelligence: impacted regression selection, missing-test proposals, candidate generated tests, dedup/validation, flaky signal, reviewable plans, approval/policy checks and provenance.
- Execution: durable jobs, queued/provisioning/running/collecting/terminal transitions, cancel/retry/timeout, isolated sandbox, CPU/memory/time/network quotas, per-org concurrency, logs/artifacts/coverage, no privileged host access.
- AI: provider gateway (Gemini plus pluggable providers), structured tool contracts, LangGraph orchestration where useful, grounded failure triage, token/cost accounting, prompt-injection defenses, user consent before private source transfer, human-approved patch/PR suggestions.
- Reports: historical metrics, audit history, downloadable evidence, GitHub Checks, actionable empty states.
- Ops: pagination, rate limiting, idempotency, queue outbox, observability, backups, retention, health/readiness, CI/CD, Docker local, Kubernetes production.

## Quality gates
Each task needs actual passing relevant tests, no broken navigation, accessible keyboard behavior, no fake backend success, no secrets in repo, no cross-tenant access. M0 specifically needs screenshots or reproducible browser verification for all eleven main screens in light and dark where feasible. UI first, backend afterward; replace demo fixtures with real data progressively. End-to-end acceptance: GitHub webhook → immutable snapshot → mining → evidence-backed risk → test plan → authorized isolated execution → failure analysis → GitHub check/report.

## Final canonical end-to-end white-box workflow
**Required flow:** GitHub repository → authorized branch/PR snapshot → repository mining (commits, diffs, dependencies, existing tests) → versioned explainable risk scoring (optional validated ML) → static white-box analysis (AST, CFG, call graph, data-flow/def-use, complexity, reachability) → coverage objective inventory (statement, decision/branch, condition, MC/DC, basis/selected feasible paths, loops, def-use, exceptions, boundaries, mutation, impacted regression) → constraint/fixture/LLM-assisted candidate test generation → validation and review → authorized hardened sandbox execution with instrumentation → measured coverage and mutation analysis → gap-driven regeneration and re-execution with bounded retries → evidence-grounded AI failure analysis → auditable dashboard/GitHub Checks and exports.

### White-box testing acceptance contract (Python and JavaScript/TypeScript)
- **Source selection:** repository, commit, base/head Git branches and pull requests; immutable SHA-pinned checkout. Git branch testing is distinct from *decision branch coverage*. Select impacted code and regression tests using dependency and history evidence.
- **Static objectives:** language-aware AST and CFG with source spans; condition/decision decomposition; feasible-path and basis-path candidate enumeration; bounded call graph; variable definitions/uses and def-use chains; loop entry/exit/boundary cases; exceptions/throws/catches/finally; input boundaries and constraints. Flag unsupported syntax, dynamic behavior, unreachable or unproven feasible objectives as `unknown`/`unsupported`, not covered.
- **Statement:** measured executed executable statements; **branch/decision:** measured outcomes for each decision (including exception edges where supported); **condition:** each atomic Boolean condition true/false where feasible; **MC/DC:** independently show each atomic condition changes the enclosing decision while other conditions are held fixed (unique-cause) or documented masking MC/DC where necessary. Require evidence of condition truth vectors, decision outcomes, executable paired tests and tool/instrumentation version; never infer MC/DC from branch coverage.
- **Basis path:** identify independent paths via CFG/cyclomatic complexity and test feasible representative basis paths; **path:** bounded feasible selected paths, not impossible exhaustive enumeration; **loop:** zero, one, two/multiple, boundary and nested cases when reachable; **data flow:** definition-use pairs and kill/redefinition behavior; **exception:** error paths, handling, propagation, cleanup; **boundary values:** type/range/empty/null/limits where applicable.
- **Mutation:** deterministic seeded mutants, applicable operator set, timeout/invalid/equivalent-or-suspected-equivalent classification, killed/survived/no-coverage results; mutation score denominator excludes invalid mutants and separately discloses suspected equivalents. **Regression:** impact-selected plus baseline suite, change-aware comparison and flakiness evidence.
- **Generation:** deterministic/constraint-based techniques first where suitable, LLM-generated test candidates as optional augmentation; syntax/type checks, assertions/oracles, fixture isolation, deduplication, review/approval and sandbox safety before execution. Generated tests are never treated as passing until actually run.
- **Measurement:** distinguish requested objectives, instrumented objectives, covered, uncovered, infeasible-proven, unknown and unsupported, per language/tool/version. Reports must show numerator/denominator, missing objectives, evidence links, run SHA, test IDs, tool versions, timeouts, and honest partial-coverage labels. No unsupported 100% coverage claim.
- **Iterative closure:** select gaps, propose targeted new tests, rerun within configured budget, stop at fixed point or budget exhaustion; show remaining gaps and why. Risk scoring prioritizes work but must never suppress mandated coverage objectives.
- **Honest scope:** aim for comprehensive *supported* white-box testing, not guaranteed exhaustive testing of arbitrary software. JavaScript dynamic constructs and Python introspection may restrict static inference; never silently mark unsupported MC/DC or path coverage complete.
